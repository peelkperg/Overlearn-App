# Epic 6 Context: Web Platform Access

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Musicians without iOS access (iOS is currently on hold; only Android ships natively) — or anyone preferring a browser — can install and use Overlearn as an offline-capable web app, matching native functionality exactly, hosted free with no ads and no new accounts. This is platform parity, not new user-facing behavior: no new FRs, all existing FR1–FR43 apply unmodified on web. The epic covers three strictly sequential capability groups that are only meaningful together: a web-compatible storage layer, PWA installability/offline shell, and GitHub Pages hosting/deploy.

## Stories

- Story 6.1: Web-Compatible Storage Layer (DONE — background only, not pending work)
- Story 6.2: Base Path & PWA Manifest Configuration
- Story 6.3: Installable Offline App Shell
- Story 6.4: GitHub Pages Deploy Workflow

## Requirements & Constraints

- No new functional requirements — web must reproduce FR1–FR43 exactly.
- NFR10: the web build must remain fully functional offline after first successful load, and be installable as a standalone PWA — not just a hosted page needing constant connectivity.
- NFR8/9 addendum (durability, not a new NFR): web's storage durability is weaker than native's — no OS sandbox, no backup mechanism; data is lost on cleared browser data, private mode, or a browser/profile switch. The "zero data leaves the device" and no-accounts guarantees themselves are unchanged.
- No backend, accounts, or telemetry may be introduced anywhere in the web-delivery surface, for any story in this epic.
- No new UI surface and no new UX-DRs — existing screens render unmodified on web via `react-native-web`.
- Non-goals (explicitly out of scope): push notifications/background sync/share-target, a custom domain, cross-browser/UAT-equivalent audit, multi-environment (staging/preview) deploy, a deploy rollback procedure.
- Success signal for the epic: a segment created and a session run to completion on the live GitHub Pages URL (not local dev) persists across reload, works offline after first load, installs via the browser's own affordance, and a direct reload on a non-root route loads the app shell rather than 404ing — with zero regressions in the existing native storage test suite.

## Technical Decisions

- **Storage (Story 6.1, done — background for 6.2–6.4):** `storage.ts` needed no `Platform.OS` branch and no hand-rolled web adapter. `react-native-mmkv@4.3.2` (pinned, unchanged) ships its own web build (`createMMKV.web.ts`), which Metro's platform-file resolution substitutes automatically — a complete `localStorage`-backed implementation, verified empirically via a clean `expo export --platform web` build. `subscribeToKeys` fan-out on web is synchronous and unsubscribable, matching MMKV's semantics, but **per-listener error isolation is unverified upstream** (no per-callback try/catch in the dependency) — flagged as a possible `deferred-work.md` entry, not something to fix in this codebase. All consumers above the storage port (`segments.ts`, `session.ts`, `history.ts`, `settings.ts`, screens) are unaffected and unchanged.
- **Base path (AD-3, Story 6.2):** exactly one named config key, `app.json#expo.extra.basePath` (e.g. `/Overlearn-App/`), is the single source of truth. The router's base URL, the PWA manifest's `start_url`/`scope`, and the service worker's registration scope (AD-8) must all read this same key directly — none may hardcode or independently re-derive the path. Revisit only as one coordinated change if a custom domain is attached later (value becomes `/`).
- **Deep-link routing (AD-4, Story 6.3):** routes past the root (`segment/[id]`, `segment/[id]/rename`, `session/[id]`) have ids created locally at runtime and are unknowable at build time — they cannot be statically prerendered and resolve client-side against local storage after the shell loads. The fallback mechanism is pinned to GitHub Pages' standard plain-copy pattern: `public/404.html` must be a byte-identical copy of the built `index.html`, generated only by the same postbuild step that generates the service worker — never hand-committed, no alternative (e.g. query-string-redirect) mechanism.
- **Service worker precache (AD-5, Story 6.3):** generated by `workbox-build`'s `generateSW` (pinned exact version, currently 7.4.1) as a postbuild step against the real static-export output (`dist/`), never hand-maintained. `globPatterns` must cover 100% of `dist/`'s files (icons and `manifest.json` included); the postbuild step must assert precached file count equals `dist/` file count (minus an explicit, named ignore list) and fail the build on mismatch. Update lifecycle uses Workbox's own default — no `skipWaiting`/`clientsClaim` — so a newly deployed worker activates only once all tabs of the old version are closed, and an in-progress session is never swapped under itself. The whole pipeline (`expo export --platform web` → `404.html` copy → `generateSW`) must be one canonical `package.json` script (e.g. `build:web`), used identically for local verification and CI/deploy — never two separately-maintained invocations.
- **Service worker registration (AD-8, Story 6.3):** exactly one call site — the web entry point / root layout's web-only boot path — calls `navigator.serviceWorker.register()` once, with no explicit `scope` passed (defaults correctly to the SW file's own location under the base path).
- **Deploy (AD-6, Story 6.4):** `.github/workflows/deploy-pages.yml` uses GitHub's native Pages Actions (`actions/upload-pages-artifact` + `actions/deploy-pages`) — not a third-party `gh-pages`-branch action. Trigger is `workflow_dispatch` only, run manually against `main` — never automatically on push, matching Android's own manual EAS build/submit release cadence.
- **No backend/accounts/telemetry (AD-7):** binds the whole web-delivery surface across all remaining stories — GitHub Pages serves static files only; the service worker caches those same static files; nothing added talks to a server.
- Stack pins relevant to this epic: `expo` ~57.0.18, `expo-router` ~57.0.17, `react-native-web` ~0.21.0, `react-dom` 19.2.3, `workbox-build` (new devDependency) 7.4.1 — verify current at install time.
- File/naming conventions: service worker at `public/service-worker.js`; SPA fallback at `public/404.html`; deploy workflow at `.github/workflows/deploy-pages.yml`.
- Single environment: GitHub Pages only, subpath `github-username.github.io/<repo>/`, no staging tier.

## Cross-Story Dependencies

- Story 6.2 (base path/manifest) and 6.3 (installable shell) both depend on Story 6.1's storage layer being correct, but 6.1 is already done — no blocking work remains there.
- Story 6.3's service worker and `404.html` generation depend on Story 6.2's base-path config existing first (the SW registration and manifest both read `basePath`).
- Story 6.4's deploy workflow depends on Story 6.3's `build:web` script (export → Workbox postbuild → `404.html` copy) existing as the single canonical build step it invokes.
- This epic has no dependency on Epics 1–5 and touches no file any of them touch.
