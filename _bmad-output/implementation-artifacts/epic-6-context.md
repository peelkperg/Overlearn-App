# Epic 6 Context: Web Platform Access

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Musicians without iOS access — or anyone preferring a browser — can install and use Overlearn as an offline-capable web app, matching native functionality exactly, hosted free with no ads and no new accounts. The web build exists specifically because no iOS build currently ships (Android-only, natively); a bare hosted URL would under-serve that goal, which is why installability and offline support are in scope alongside the storage swap, not deferred.

## Stories

- Story 6.1: Web-Compatible Storage Layer
- Story 6.2: Base Path & PWA Manifest Configuration
- Story 6.3: Installable Offline App Shell
- Story 6.4: GitHub Pages Deploy Workflow

## Requirements & Constraints

- No new user-facing functional behavior — every existing FR must work identically on web; this epic is platform parity, not new capability.
- The web build must remain fully functional offline after the first successful load, installable as a standalone app — not a hosted page requiring constant connectivity.
- Web's storage durability is weaker than native's (no OS sandbox, no backup mechanism; data lost on cleared browser data, private mode, or a browser/profile switch) — this is documented, not fixed; native's "zero data leaves the device" / "no accounts" guarantees are unchanged and apply identically on web.
- No backend, accounts, or telemetry may be introduced to support hosting or installability, on either platform.

## Technical Decisions

- `storage.ts` stays a single port with platform-selected adapters (MMKV native / `localStorage` web). Its public API and signatures are unchanged for both platforms — no call site above the storage boundary changes. The quarantine convention (`{key}.corrupt.{timestamp}`) and versioned-envelope migration chain are reused as-is. Critically, **construction itself** (not only the calls made on the store) must be gated by `Platform.OS` — today the native store is constructed unconditionally at module load, which would crash a web import if left as-is.
- `subscribeToKeys` on web: an in-module listener `Set`, fired synchronously on every `set`/`remove` (matching MMKV's same-process semantics), each callback invoked in its own try/catch (one throwing listener must not block siblings or the write), with a registration handle exposing `.remove()` for clean unsubscribe.
- Exactly one named config key, `app.json#expo.extra.basePath`, is the single source of truth for the router's base URL, the PWA manifest's `start_url`/`scope`, and the service worker's registration scope. None of the three may hardcode or independently re-derive it. Value: the GitHub Pages subpath (e.g. `/Overlearn-App/`) for now — no custom domain yet.
- Dynamic routes (`segment/[id]`, `segment/[id]/rename`, `session/[id]`) have ids created locally at runtime and can't be statically prerendered — they resolve client-side against local storage after the shell loads. A GitHub Pages SPA-routing fallback is required, not optional: `public/404.html` as a byte-identical copy of the built `index.html`, generated in the same postbuild step that generates the service worker (single owner, never hand-committed).
- Service worker precache: generated by `workbox-build`'s `generateSW` (pinned exact version, currently `7.4.1`) as a postbuild step against the real static-export output, covering 100% of `dist/` — a file-count assertion fails the build on mismatch. Update lifecycle uses Workbox's conservative default (no `skipWaiting`/`clientsClaim`): a newly deployed worker activates only once every tab running the old version has closed, so an in-progress practice session is never swapped under itself. One canonical `build:web` `package.json` script runs the whole pipeline (`expo export --platform web` → `404.html` copy → `generateSW`), used identically for local verification and CI.
- Service worker registration lives in exactly one file (the web entry point / root layout's web-only boot path), called once, with no explicit `scope` passed — it defaults correctly from the service worker's own location under the base path.
- Deploy: GitHub's native Pages Actions (`actions/upload-pages-artifact` + `actions/deploy-pages`), not a third-party `gh-pages`-branch action. Trigger is manual (`workflow_dispatch`) only — never automatic on push to `main` — so web release timing is a deliberate choice, matching Android's own manual EAS build/submit cadence.

## Cross-Story Dependencies

Sequential, none depending on a later story: 6.1 (storage) has no dependency; 6.2 (base path/manifest) is independent infrastructure; 6.3 (installable shell) needs 6.2's `basePath` value to exist; 6.4 (deploy workflow) needs 6.3's `build:web` script to exist. No dependency on Epics 1–5 in either direction — this epic touches `storage.ts` only additively (a new platform branch) without changing existing native behavior.
