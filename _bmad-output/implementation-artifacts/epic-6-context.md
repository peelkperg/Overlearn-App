# Epic 6 Context: Web Platform Access

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Musicians without iOS access — or anyone preferring a browser — can install and use Overlearn as an offline-capable web app, matching native functionality exactly, hosted free on GitHub Pages with no ads and no new accounts. This is platform parity, not new user-facing behavior: no new FRs, no new UI surface — every existing screen renders unmodified on web via `react-native-web`. The epic is one unit, not three, because storage web-parity, installability, and hosting/deploy are strictly sequential and none is independently meaningful alone.

## Stories

- Story 6.1: Web-Compatible Storage Layer
- Story 6.2: Base Path & PWA Manifest Configuration
- Story 6.3: Installable Offline App Shell
- Story 6.4: GitHub Pages Deploy Workflow

## Requirements & Constraints

- No new functional requirements — web reuses FR1–FR43 unmodified.
- NFR10: the web build must remain fully functional offline after the first successful load, and be installable as a standalone PWA — not merely a hosted page requiring constant connectivity.
- NFR8/9 (zero data leaves the device, no accounts/auth/user-identification) hold identically on web — unchanged, not relaxed.
- Web-only durability addendum to NFR8/9 (documentation-only, no behavior change): web storage lacks an OS sandbox and backup mechanism, so data is lost on cleared browser data, private/incognito mode, or a browser/profile switch. This is a disclosed platform-capability gap, not a spec violation.
- No backend, account system, or telemetry may be introduced anywhere in the web-delivery surface.
- Stories are ordered as a hard dependency chain: storage parity (6.1) blocks installability (6.2, 6.3), which blocks hosting/deploy (6.4). No dependency on Epics 1–5; this epic touches no file any of them touch.

## Technical Decisions

Full detail lives in `ARCHITECTURE-SPINE.md` (`_bmad-output/planning-artifacts/architecture/architecture-Overlearn-App-2026-09-13/`), amended 2026-09-14 during Story 6.2 build investigation. The summary in `architecture.md`'s "Web Platform Architectural Decisions" section predates that amendment and is stale on AD-1/AD-2/AD-3 — treat the spine as authoritative.

- **AD-1 (storage port), amended:** `storage.ts` needs **no** hand-rolled `Platform.OS`-gated adapter. `react-native-mmkv@4.3.2` (pinned, unchanged) ships its own web build (`createMMKV.web.ts`), which Metro's platform-file resolution substitutes automatically — a complete `localStorage`-backed implementation covering construction and every raw-store method already used. Verified empirically: an unmodified `storage.ts` exports clean for web and the bundle contains the web module's implementation. `getObject`/`setObject`, `migrate`, `quarantine`, and the versioned-envelope/quarantine conventions are reused unmodified on both platforms.
- **AD-2 (listener fan-out), amended:** the same dependency's web build already provides synchronous, same-tick listener fan-out via an in-module `Set` and a `.remove()`-bearing unsubscribe handle — no code in this repo implements it. **Not yet verified:** per-listener error isolation (the dependency's `listeners.forEach` has no per-callback try/catch) — confirm with a test before relying on it; log to `deferred-work.md` if it doesn't hold.
- **AD-3 (base path), amended:** exactly one named config key is the source of truth for the router base, the PWA manifest `start_url`/`scope`, and the service worker's registration scope: **`app.json`'s `expo.experiments.baseUrl`** — not `expo.extra.basePath` (the originally specified key, found during Story 6.2 to be one `@expo/cli`'s static-export pipeline never reads; `experiments.baseUrl` is what `getBaseUrlFromExpoConfig` actually applies to routing and asset URLs). Set to the GitHub Pages subpath (e.g. `/Overlearn-App/`) for now; a future custom domain changes this one key to `/`, not three independent places.
- **AD-4 (deep-link fallback):** `segment/[id]`, `segment/[id]/rename`, `session/[id]` are user-created at runtime and unknowable at build time, so no static HTML can exist for them ahead of time. `public/404.html` is a byte-identical copy of the built `index.html`, generated in the same postbuild step as the service worker (never hand-committed) — GitHub Pages' standard SPA fallback pattern, not a query-string-redirect trick.
- **AD-5 (service worker precache):** generated by `workbox-build`'s `generateSW` (pin `7.4.1`) as a postbuild step against the real `dist/` output — never hand-maintained. `globPatterns` must cover 100% of `dist/` (icons and `manifest.json` included); the postbuild step asserts precached file count equals `dist/` file count (minus a named ignore list) and fails the build on mismatch. Update lifecycle uses Workbox's conservative default — no `skipWaiting`/`clientsClaim` — so a newly deployed worker activates only after every old-version tab closes; an in-progress practice session is never swapped under itself. One canonical `build:web` script (`expo export --platform web` → `404.html` copy → `generateSW`) serves both local verification and CI.
- **AD-6 (deploy):** `.github/workflows/deploy-pages.yml` builds via `build:web` and publishes via `actions/upload-pages-artifact` + `actions/deploy-pages`, triggered only by `workflow_dispatch` against `main` — never on push. Deploy timing is a deliberate human choice, matching Android's manual EAS cadence.
- **AD-7 (no backend):** GitHub Pages serves static files only; the service worker caches those same static files; nothing in this surface talks to a server.
- **AD-8 (SW registration):** registration lives in exactly one file — the web entry point / root layout's web-only boot path — called once, with no explicit `scope` passed (it defaults correctly from the service worker's own location under the base path per AD-3).

Stack additions/pins for this epic: `react-native-web ~0.21.0`, `react-dom 19.2.3`, `workbox-build 7.4.1` (new devDependency — verify current at install time). Existing pins unchanged: `expo ~57.0.18`, `expo-router ~57.0.17`, `react-native-mmkv 4.3.2`.

File ownership for this epic: `src/lib/storage.ts` (AD-1, AD-2 — no other call site above the storage port changes), `app.json` (manifest fields + `expo.experiments.baseUrl`, AD-3), `public/service-worker.js` + `public/404.html` (generated only, by the `build:web` postbuild step — never hand-committed, AD-4/AD-5), the web entry point's SW registration call (AD-8), `.github/workflows/deploy-pages.yml` (AD-6).

## Cross-Story Dependencies

- Story 6.1 (storage web-parity) is a blocking prerequisite for 6.2 and 6.3 — nothing above the storage port can be exercised on web until it works.
- Story 6.2 (base path / manifest) must land before 6.3, since the service worker's registration scope and the manifest's `start_url`/`scope` both derive from the same `expo.experiments.baseUrl` key.
- Story 6.3 (installable offline shell) must land before 6.4 — the deploy workflow runs the same `build:web` script 6.3 defines; there is no separate CI-only build path.
- No dependency on Epics 1–5, and no file overlap with them.
