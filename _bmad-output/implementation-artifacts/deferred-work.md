## Deferred from: code review of 4-6-view-segment-list-row-summary-data (2026-09-12)

- **Two write-only screens now pay the full `O(segments × history)` aggregates cost.** `src/app/segment/new.tsx:14` and `src/app/segment/[id]/rename.tsx:19` call `useSegments()` solely to pull `createSegment` / `renameSegment` — they never read `segments` or `aggregates`. Story 4.6 removed the `needsHistory` gate, so each now registers a `subscribeToAnyHistory` listener and runs `buildSortAggregates(rawSegments)` on mount, re-running it on every `history.<id>` write while mounted. This is the **same issue already deferred from Story 4.3's review** (see below), whose entry notes the accepted gate "already removes most of the cost" — precisely the cost this change restores. Deferred for the same reason as the original: the clean fix is the hook split (a list-specific hook vs. a writers-only hook), a design change beyond this story's scope. Verified mitigating detail: `rename.tsx` keystroke re-renders do **not** recompute, since `[rawSegments, historyVersion]` are both stable across local state changes.

- **Aggregates recompute on segment-list mutations, not only history writes.** The memo key is `[rawSegments, historyVersion]`, so a rename — which changes `rawSegments` identity and nothing about history — triggers a full aggregates sweep that cost zero under name/createdAt sort before. FR41 requires only history freshness. Deferred because the saving is narrower than it first appears: a created or duplicated segment genuinely needs a new aggregate entry, so only rename (and arguably delete) is pure waste, and separating those cases means keying the memo on something finer-grained than array identity.

- **Every row re-renders on every history write.** `buildSortAggregates` constructs fresh objects per call and `aggregates` is a new `Map` on each `historyVersion` bump, so `aggregates.get(item.id)` hands every `SegmentListItem` a new prop reference; `sorted` now depends on `aggregates`, so the array identity churns too. No `React.memo` on the row could help as written. Deferred as a pure performance concern with no correctness impact at this project's data scale; revisit together with the hook split above, since both are addressed by the same restructuring.

- **A segment name containing a comma makes the row's accessibility announcement structurally ambiguous.** The template `${name}, last practice …, solidification …, created …` gives a screen-reader user no way to tell the user-supplied name from the generated fields — a name like `Bar 24, last practice 1 Jan 2020` announces a fabricated practice date. Deferred as the same class as the already-logged apostrophe (Story 5.3) and literal-quote (Story 4.2) entries: this is a copy/delimiter decision to make once across every name-in-string site, not a defect to patch silently in one of them.

- **`buildSortAggregates` picks `lastPracticed` by raw string `>` comparison.** `isValidIsoDate` accepts any `Date.parse`-able string, not only ISO-8601, so a history array mixing `"Sep 10 2026"` with `"2026-09-08T…"` makes the max-pick lexicographic garbage (`"Sep…" > "2026-…"` is always true) and the row shows a non-latest entry as "last practice". Pre-existing from Story 4.3; surfaced only because Story 4.6 is the first code to display the result rather than just sort by it. Deferred as pre-existing and unreachable through the app's own writers, which always emit ISO.

- **Moving the name into an unstyled wrapper `View` may shift where the name truncates.** `src/components/SegmentListItem.tsx:202` — the `numberOfLines={1}` name label is now a child of a style-less `View` inside a flex row rather than a direct child of the `Pressable`, which can change the measured width. No breakage observed; flagged as untested rather than as a known defect.

- **The UX spec's cited type precedent for the summary lines is factually wrong.** `ux-design-specification.md`'s FR41 section says lines 2-3 use "the small/secondary label type already used for the sort menu's non-selected items", but `SortControl.tsx:97` renders non-selected items as `type="default"`. ## Deferred from: code review of 5-2-apply-a-changed-target-to-an-in-progress-session (2026-09-12, round 2)

- **A version downgrade quarantines every persisted key, not just sessions.** `SCHEMA_VERSION` went to 2 in Story 5.2, and `setObject` stamps `__v: 2` on every shape it writes — `segments`, `history.{id}`, `settings.general` and `session.active` alike. On a build where `SCHEMA_VERSION === 1`, `migrate(2, data)` skips its `while` loop and returns `undefined` for all of them, so `getObject` quarantines each key: the user opens the app to zero segments and zero history. `quarantine()`'s first-corruption-wins rule also means a later corruption on the downgraded build cannot be preserved alongside the rollback backup. Deferred because the "a version newer than this build knows about has no path forward and is treated as unreadable" rule is **documented intent** from the envelope's original design (`src/lib/storage.ts:72-76`, 2026-09-05 NFR assessment) — Story 5.2 is simply the first-ever bump to make that branch reachable. Making reads forward-compatible (e.g. accepting a newer envelope when the shape is unchanged, or only quarantining keys whose shape actually changed between versions) is a storage-design decision with its own failure modes, not a local patch. Revisit before any release that could plausibly be rolled back, or at the next `SCHEMA_VERSION` bump — whichever comes first.
