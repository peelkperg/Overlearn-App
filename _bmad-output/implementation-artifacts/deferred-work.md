# Deferred Work

Items surfaced by review workflows that were real but not actionable at the time they were found.

## Deferred from: code review of 5-3-see-a-warning-before-changing-settings-mid-session (2026-09-11)

- **`accessibilityLiveRegion="polite"` on a node that mounts and unmounts never actually announces.** A polite live region fires when its *content* changes; the FR39 notice instead appears and disappears wholesale, so on Android it announces once on mount and never again — including on the very stepper taps it is warning about — and on iOS the prop is a no-op entirely. Deferred because it is both pre-existing and spec-mandated: UX-DR24 names this exact prop, `ux-design-specification.md`'s accessibility section explicitly wants the notice "read as part of the screen's normal content when Settings opens with a session active — it is not an alert interruption", and the same Android-only limitation is already logged against the duplicate snackbar from Story 4.2's review. Revisit alongside that entry as part of any iOS port, where the whole `accessibilityLiveRegion` pattern (6 sites since v1.0) needs a parity decision rather than a per-site patch.

- **A segment name containing an apostrophe garbles the notice's quote wrapping.** `You have a session in progress for '${name}.'` renders `for 'Bach's Bar 24.'` for a segment named `Bach's Bar 24` — the quote boundary and the sentence end both become ambiguous. Apostrophes are common in musical naming. Deferred for the same reason as the near-identical Story 4.2 entry above (a literal `"` in the duplicate snackbar): the string is specified verbatim in Story 5.3's AC #1 and in `epics.md:801`, so changing the quoting — typographic quotes, or dropping quotes entirely — is a UX copy decision to make deliberately across every name-quoting site at once, not a defect to patch silently in one of them.

- **The UX spec's "Layout, top to bottom" enumeration still lists the in-progress notice fifth while it ships second.** Item 5's own body says "shown above the stepper" (item 2), and Story 5.1 already adjudicated in favour of that placement, which AC #1 and the shipped code both follow. Deferred because it is a residual numbering inconsistency in a document section this story only touched for copy, and renumbering the list invites re-litigating the order rather than just correcting it.

- **`traceability-matrix.md` still marks FR39 PLANNED.** So does it for FR35–FR37, which Stories 5.1 and 5.2 shipped. Deferred because this is pre-existing project-wide drift rather than a Story 5.3 regression, and the fix is one pass over the whole matrix after Epic 5 closes, not a single-row edit mid-epic.

## Deferred from: code review of 5-2-apply-a-changed-target-to-an-in-progress-session (2026-09-11)

- **Stepper `disabled` guard and styling still read the stale render-time value the `onPress` fix was written to escape.** `src/app/settings.tsx` now computes the written value from `readSettings().overlearningPercent` (Story 5.1's review fix for the double-tap race), but `disabled={settings.overlearningPercent <= 50}` and the dimmed-button style still come from the closed-over render snapshot. During exactly the window the fix exists to cover, the guard accepts or rejects a tap on a stale percent while the write computes from the fresh one. Deferred because it is unreachable today — `setOverlearningPercent`'s own clamp to [50, 300] makes the disagreement unobservable — and because the obvious "read fresh in render too" fix would put a storage read in the render path, violating render purity; the clean fix is to confirm `useSettings()`'s subscription already delivers a post-commit-fresh value and drop the `readSettings()` call instead. Revisit if the boundary rule ever stops being a clamp (e.g. reject-and-warn, or a different max).

- **Disabled-stepper tests verify the storage clamp, not that the control is inert.** `src/app-tests/settings.test.tsx`'s boundary tests press `settings-decrease` at 50% and assert the displayed value and `readSettings().overlearningPercent` are unchanged — but `setOverlearningPercent` clamps, so both tests pass with `disabled={...}` removed from both `Pressable`s entirely. The tests' own comment claims to confirm the button "is actually inert, not just visually dimmed"; they do not. Deferred because the fix means spying on `setOverlearningPercent` (or asserting the press handler is never invoked), which introduces a mocking pattern this suite has not used before — worth doing deliberately alongside the item above, since both concern the same boundary behavior.

## Deferred from: code review of 4-3-sort-the-segment-list (2026-09-08)

- **`useSegments()` now sorts for every consumer, not just the list screen.** Story 4.3 added sorting and a conditional history subscription to the shared hook, but `src/app/segment/new.tsx` and `src/app/segment/[id]/rename.tsx` both call `useSegments()` and destructure only a writer function (`createSegment` / `renameSegment`). With a history-dependent sort key persisted, each of those screens independently mounts a `subscribeToAnyHistory` listener and rebuilds the aggregates map on every render, then discards the sorted array. Correctness is unaffected — only wasted work. Deferred because the clean fix is a hook split (a list-specific hook vs. a writers-only hook), which is a design change beyond this story's scope and touches call sites Story 4.3 was told not to widen; the accepted patch that gates `buildSortAggregates` behind the history-dependent sort keys already removes most of the cost.
- **The AC #6 persistence test does not actually simulate a cold start.** `src/app-tests/index.test.tsx`'s "persists the selected sort option and direction across a relaunch" unmounts and re-renders `<HomeScreen />` in the same JS realm, so `lib/settings.ts`'s module-level `snapshot`/`cachedRaw` cache stays warm across the simulated relaunch. Persistence through MMKV genuinely is verified (a broken `setObject` fails the pre-unmount assertion), and `settings.test.ts` covers cold reads for the empty and corrupt cases — but the "valid payload read cold from storage" path is unexercised. Deferred because closing it properly means introducing `jest.resetModules()` into a suite that has never used it, which affects the shared-MMKV-mock contract documented in `jest.setup.js`; worth doing deliberately alongside any future test-infrastructure work rather than as a one-off in this story.

## Deferred from: code review of 4-2-duplicate-a-segment (2026-09-06)

- **Disambiguation suffix can push a name past the 80-character cap.** `SegmentForm` caps typed input at 80 chars (`MaxNameLength`), but `disambiguate` appends `" (N)"` programmatically with no length re-check, and `isSegmentArray` doesn't validate length either. Deferred because it is **pre-existing, not introduced by Story 4.2**: `createSegment` reaches the identical append path, so creating two same-named 80-character segments already overflows in shipped v1.0. Fixing it properly means deciding truncation semantics (truncate the base name? refuse? allow?) across create, rename, and duplicate together — a spec question, not a local patch.
- **`accessibilityLiveRegion="polite"` is Android-only.** It has no effect under iOS VoiceOver, so on iOS a screen-reader user would get no announcement for the duplicate confirmation — the exact case the notice exists to cover. Deferred because it is pre-existing and spec-mandated: UX-DR24 names this precise prop, it is the established pattern in five source files since v1.0, and iOS has never been built or verified in this project (see the backlog's iOS support entry). Revisit as part of any iOS port, alongside the other accessibility-parity work already listed there.
- **A literal `"` in a segment name garbles the confirmation notice.** `Duplicated as "${copy.name}"` renders `Duplicated as "Bar "24" (2)"` for a segment named `Bar "24"`. Cosmetic only; the name itself stores and displays correctly everywhere else. Deferred because the notice string was specified verbatim in Story 4.2's Task 4 — changing the quoting (typographic quotes, or dropping quotes entirely) is a UX copy decision to make deliberately rather than a defect to patch silently.

## Deferred from: code review of 4-1-rename-a-segment (2026-09-06)

- **Generic `catch` in the Rename screen misattributes non-storage failures.** `src/app/segment/[id]/rename.tsx`'s `handleSubmit` collapses every throw into "Could not rename that segment. Check that the device has free storage." `renameSegment` also throws on an empty name and on an unknown segment id, neither of which is a storage problem. Deferred because: (a) the identical generic-catch pattern is the established convention in `src/app/segment/new.tsx`, so changing only the new screen would introduce an inconsistency; (b) both non-storage throw paths are unreachable in practice today — `SegmentForm` blocks submission of an empty/whitespace-only name before `onSubmit` fires, and this single-user offline app has no path to delete a segment while its Rename screen sits on top of the navigation stack. Revisit if either invariant changes (e.g. FR40's inline rename bypasses `SegmentForm`'s validation, or any background/multi-surface mutation is introduced).

## Deferred from: code review of 4-4-view-a-segments-solidification-percent (2026-09-10)

- **Zero-attempt history entries render the em dash while history rows are visible.** A segment whose entries all carry `totalAttempts: 0` makes `calculateSolidificationPercent` return `null`, so the Segment Detail screen shows "Solidification: —" ("no data yet") directly above a populated history list — a self-contradictory display. Reachable only via shape-valid-but-nonsensical stored data: `isHistoryEntryArray`'s `isNonNegativeInteger` admits `0`, while a real completed session always records at least the minimum-5 target streak's worth of attempts. Deferred because the app's own write path cannot produce this state, and guarding it would add a display branch for a condition the mechanic makes unreachable. Revisit if `isHistoryEntryArray` ever gains a positive-attempts invariant, or if FR38's display is reused somewhere fed by imported/migrated data.

## Deferred from: code review of 4-5-rename-a-segment-inline (2026-09-10)

- **The inline error grows the segment row and reflows the rows below it.** `inlineInput` carries `flex: 1` inside `rowLabel`, which is a column with `justifyContent: 'center'` and `minHeight: 44`; rendering the "Name must not be empty" `ThemedText` adds a second column child, pushing the row past its minimum height and shifting every FlatList row beneath it. Deferred rather than patched because AC #1's "no shift in the row/heading's layout" constrains *entering edit mode*, not error display, and reflow-on-validation-error is the conventional behavior — constraining it (absolute positioning, or reserving vertical space in the static state) is a UX decision with its own cost, not an obvious defect. Noted explicitly as **introduced by this change, not pre-existing**. Revisit alongside the detail-heading layout-shift decision from the same review, which covers the genuine AC #1 violation.
