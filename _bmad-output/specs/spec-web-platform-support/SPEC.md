# Web Platform Support

## Why

Overlearn only runs natively on iOS/Android — its sole persistence module is built directly on `react-native-mmkv`, which has zero web support. Right now no iOS build ships at all (only Android does, natively), so a web build is the path to reach the users the native side currently excludes entirely. It needs to be free, ad-free, and require no new accounts — the app's existing zero-accounts/zero-telemetry posture carries over unchanged.

## Capabilities

- **CAP-1**
  - **intent:** `storage.ts` works correctly on web with the same public API every layer above it already relies on. (Verified 2026-09-14: `react-native-mmkv@4.3.2`, already pinned, ships its own web implementation Metro substitutes automatically — no code change needed in `storage.ts` itself; this capability is satisfied by test coverage confirming existing behavior, not new adapter code.)
  - **success:** a segment/session/history created via a web build persists across a page reload identically to native; existing native storage tests pass unmodified; new web-path tests confirm quarantine, migration, `subscribeToKeys` sync notify + unsubscribe, and storage-unavailable degradation against the dependency's real web build. Per-listener error isolation is unverified upstream (the dependency's fan-out has no per-callback try/catch) — test for it; if it doesn't hold, that's a `deferred-work.md` entry against the dependency, not this codebase.

- **CAP-2**
  - **intent:** the web build is installable and loads its app shell with zero connectivity after first load, matching native's offline-first experience for the users this web build exists to reach.
  - **success:** the browser's install affordance works; a deployed build with the network disabled after first load still boots and functions; a direct reload on a non-root route still loads the app shell, not a 404.

- **CAP-3**
  - **intent:** the web build deploys to GitHub Pages via GitHub's native Pages Actions, at a repo subpath (no custom domain for now), triggered manually rather than on every push to `main`.
  - **success:** a manually triggered workflow run produces a live, reachable deployment at the GitHub Pages URL; a segment/session run to completion on that live URL persists across reload, matching the local-dev-server check.

- **CAP-4**
  - **intent:** `prd.md` documents the web build's weaker durability guarantee (no OS sandbox; vulnerable to browser-data clearing or a profile switch), while the "zero data leaves the device" guarantee itself is unchanged.
  - **success:** `prd.md` contains the NFR8/9 addendum.

## Constraints

- `storage.ts`'s public API and signatures are unchanged for both platforms; no call site above the storage boundary changes, and no `Platform.OS` branch or hand-rolled web adapter is added — `react-native-mmkv`'s own web build already satisfies the contract. The quarantine convention and versioned-envelope migration chain are reused as-is — no parallel implementation.
- `subscribeToKeys` fires synchronously on every `set`/`remove` on web (provided by the dependency), with an explicit, MMKV-shaped unsubscribe handle. Per-listener error isolation is not guaranteed by the dependency's current implementation — verify with a test rather than assume.
- Base path is one named config key (`app.json#expo.extra.basePath`), read directly by the router, the PWA manifest, and the service-worker registration — none re-derives it independently.
- The service worker's precache is generated by Workbox (`workbox-build`, pinned exact version) from the real static-export output, covering 100% of `dist/` — never hand-maintained. Its update lifecycle uses Workbox's conservative default, so an in-progress session is never swapped under itself.
- No backend, accounts, or telemetry are introduced to support hosting or installability — GitHub Pages serves static files only.
- Deploy runs through GitHub's native Pages Actions (`actions/upload-pages-artifact` + `actions/deploy-pages`) only, not a third-party `gh-pages`-branch action, triggered manually (`workflow_dispatch`) — never automatically on push to `main`.

## Non-goals

- The full PWA feature surface beyond installability/offline shell (push notifications, background sync, share-target) — no driver to add them.
- A custom domain — subpath deploy accepted for now.
- A full cross-browser/UAT-equivalent audit — this covers booting, installing, and deploying, not exhaustive polish.
- Multi-environment (staging/preview) deploy — single production environment only.
- A deploy rollback procedure — explicitly deferred, not decided.

## Success signal

A segment created and a practice session run to completion on the live GitHub Pages URL (not the local dev server) persists across a reload, the app works offline after first load, installs via the browser's own affordance, and a direct reload on a non-root route loads the app shell rather than 404ing — all with zero regressions in the existing native storage test suite.
