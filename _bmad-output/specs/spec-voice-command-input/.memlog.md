- (note) Stakeholder Lens Rotation (elicitation) surfaced 4 gaps: (1) instrument/room noise as a false-trigger source, pushing toward push-to-talk over always-listening; (2) freely user-typed command words risk unreliable recognition, especially for non-native speakers; (3) TalkBack/VoiceOver mic-conflict; (4) microphone permission is a first for this app, needs an explicit privacy statement parallel to NFR8/9.
- (decision) Gap 3 (accessibility/TalkBack interaction) explicitly out of scope, per Gerardo: this feature's target is logging correct/incorrect attempts when hands are busy during practice, not an accessibility feature; screen-reader interaction would need deeper analysis this feature doesn't intend to do.
- (decision) Activation model: wake-word gated (e.g. a trigger word before the correct/incorrect command), reducing instrument/room-noise false triggers vs. always-listening. Additionally, the Active Session screen must expose an explicit mic on/off toggle for voice commands -- the mic only listens when the user has turned it on, never by default.
- (decision) Command mechanism is recorded-sound template matching, not speech-to-text word recognition. User records three custom sound triggers -- wake word, Correct, Incorrect -- each can be any sound (word, clap, hum, tap), not constrained to language/vocabulary. This sidesteps the non-native-speaker accent-reliability problem entirely (no ASR vocabulary dependency). Real architecture-feasibility question: what on-device tech performs reliable single/few-shot custom sound matching (vs. standard ASR, which needs a fixed vocabulary) -- flagged for architecture research, not resolved in this spec.
- (decision) Recording flow: single take per trigger (wake/Correct/Incorrect), but the app runs a distinguishability check across all three recorded sounds before allowing save, rejecting/warning if any two are too acoustically similar to reliably tell apart.
- (constraint) On-device audio matching only, hard constraint -- no cloud speech/audio API ever, no recorded trigger sample leaves the device, consistent with NFR8/9's zero-telemetry/offline-only posture. Microphone OS permission is requested only the first time the user turns on the voice-command toggle on the Active Session screen, never upfront at install/onboarding.
- (capability) CAP-1: hands-free Correct/Incorrect logging during an active session via wake-then-command recorded-sound triggers, equivalent effect to tapping the Correct/Incorrect buttons.
- (capability) CAP-2: explicit mic on/off toggle on the Active Session screen; mic is inactive by default and only captures audio while toggled on.
- (capability) CAP-3: user records three custom trigger sounds (wake, Correct, Incorrect); save is blocked with a rejection/warning if any two are not acoustically distinguishable.
- (question) Open question (unresolved, needs architecture research): what on-device technique performs reliable single/few-shot custom-sound matching, as opposed to fixed-vocabulary ASR -- referenced from memlog decision on recorded-sound template matching.

- (decision) Resolved open question: on-device matching technique is DTW (Dynamic Time Warping) over MFCC features, not TFLite audio embeddings. Reason: no ML model to bundle, no new native dependency, adequate for a small 3-template set (wake/Correct/Incorrect); embeddings would need TFLite runtime + model, requiring separate dependency-governance approval, larger app size, higher CPU draw while listening. Distinguishability check (CAP-3) implemented as a DTW-distance threshold between the three recorded templates.
- (event) Re-derived SPEC.md: open question resolved, added companion stack.md (HOW-level matching-technique detail, Spec Law rule 2 keeps kernel intents WHAT-only). companions: [stack.md]. Open Questions section now empty/omitted.
- (capability) CAP-4: user can turn the wake-word requirement on or off, independent of CAP-2's mic on/off toggle. With wake-word ON (default), CAP-1's wake-then-command flow applies unchanged -- only a wake match opens the Correct/Incorrect command window. With wake-word OFF, the matcher skips the wake gate entirely and matches Correct/Incorrect triggers directly against every live audio window, no preceding wake sound required. Intended use: ON for noisy practice environments (instrument playing, wake word filters ambient false triggers), OFF for quiet environments where the user wants fewer sounds to make per repetition.
- (constraint) Recording duration cap: each of the three trigger recordings (wake, Correct, Incorrect) is capped at 2 seconds -- recording auto-stops at 2 seconds if the user has not already stopped it manually. Applies uniformly across CAP-3's recording flow regardless of CAP-4's wake-word setting.
- (decision) CAP-4 (wake-word off) removes the wake-gate's false-positive protection entirely for that mode -- matching runs directly against every live window using only the Correct/Incorrect templates. This is an accepted trade-off of the user's own choice (quiet-environment use case), not a gap: the risk CAP-1's wake-gating originally existed to bound (ambient instrument/room noise) is explicitly what the user is signaling is absent when they choose wake-word-off.
