- `handleDone` (`src/app/session/[id].tsx:44-54`) wrote the history entry, then cleared the session, as two separate MMKV writes with no atomicity between them. If the app was killed in the narrow window between the two, relaunch restored a `sessionComplete: true` session that still routed to the Completion screen, and a second Done tap wrote a duplicate history entry for the same practice run (FR29). `edge`

A kill mid-sequence can leave an orphaned `history.<id>` or `session.active` key — invisible to the user, not corrupting. The risk window is a single JS tick between synchronous MMKV writes, and the current order already fails toward harmless orphaned data rather than visible loss. No change made. `edge`

IncorrectButton's touch area minus the 44×44 Restart chip still leaves the large majority of the ~40% zone tappable. No change made. `auditor`

### Patch

- [x] [Review][Patch] **FIXED.** **CRITICAL, empirically confirmed.** `logCorrect`/`logIncorrect`/`restart`/`start` in `src/hooks/useActiveSession.ts` all compute `next` from the `session` value captured in the current render's closure, then call `setSession(next)` — not `setSession(prev => ...)`. Two calls issued before React commits the first (e.g. `result.current.logCorrect(); result.current.logCorrect();` in the same synchronous block) both read the same stale `session`; the second overwrites the first instead of compounding. Verified with a diagnostic test: two `logCorrect()` calls in one `act()` block leave `currentStreak` at 1, not 2 — one real repetition is silently dropped from both MMKV and UI state. This is the core mechanic's counting guarantee (FR16/FR18) failing under a plausible double-tap. `blind+edge`
- [x] [Review][Patch] **FIXED.** `settled` (completion visual/haptic flag) never resets — `useFeedbackSignal.ts` exposes no reset, and neither `start()` nor `restart()` in `useActiveSession.ts` clears it. Story 2.8's Repeat flow calls `start()` on the same mounted hook instance without navigating away, so a brand-new incomplete session begins while `settled` is still `true` from the prior completion. `blind`
- [x] [Review][Patch] **FIXED.** `pulseTimer`/`flashTimer` (`useFeedbackSignal.ts:18-19,30-33,41-44`) are never cleared on unmount — no cleanup effect. A pending timeout firing after unmount calls `setIncorrectPulse`/`setTargetRaiseFlash` on a gone component; on Repeat it can visually bleed a stale flash/pulse into the newly-started session. `blind+edge`
- [x] [Review][Patch] **FIXED.** `useActiveSession` does not subscribe to session-storage change notifications, unlike `useSegments` (which now does, per Epic 1's fix). `app/index.tsx` and `app/session/[id].tsx` each mount their own `useActiveSession()` instance; a completion or discard in one is invisible to the other until it independently re-reads. Since Expo Router's Stack keeps `index.tsx` mounted underneath `session/[id].tsx`, navigating back can show a stale Resume/Discard dialog for a session that already completed or was cleared. `auditor`
- [x] [Review][Patch] **FIXED.** `Vibration.vibrate()` and `AccessibilityInfo.announceForAccessibility()` in `useFeedbackSignal.ts:39-40,52` are unguarded, unlike every `Haptics.*` call in the same file (`.catch(() => {})`). A throw from either propagates out of `logCorrect`/`logIncorrect`'s press handler, uncaught by any boundary — after the state write already succeeded. `edge`
- [x] [Review][Patch] **FIXED with Decision 1.** `handleDone` (`src/app/session/[id].tsx:46`) wrote history keyed on the raw route param `id`, not `segment.id` — inconsistent with the rest of the screen, which operates on the resolved segment. Also, this screen was not updated to use Epic 1's `useRouteId` guard against an array-valued or undefined param.
- [x] [Review][Patch] **FIXED.** `calculateTargetStreak` (`src/lib/mechanic.ts:10-12`) and `isSessionState` (`src/lib/types.ts:77,79`) have no `Number.isFinite` guard. A `NaN`/`Infinity` `totalIncorrectThisSession` — reachable only through corrupted-but-typeof-number storage — makes `currentStreak >= targetStreak` permanently false, soft-locking the session with no route to completion.
- [x] [Review][Patch] **FIXED.** `ResumeDiscardDialog`'s `<Modal>` (`src/components/ResumeDiscardDialog.tsx:16`) has no `onRequestClose`, unlike `RestartConfirmDialog`, which sets one explicitly. On Android this logs an RN dev warning; functionally the back button already does nothing (matching FR24's "never silently dismissed" intent), but the sibling dialog handles this deliberately and this one doesn't.
- [x] [Review][Patch] **FIXED.** Restart control text fails WCAG AA contrast: `restartText: '#8a8a8a'` on `restartBackground: '#2a2a2a'` (`src/components/session/colors.ts:16-17`) computes to ≈4.2–4.3:1 at 11px, below the 4.5:1 normal-text minimum (11px doesn't qualify for the 3:1 large-text exception). Violates Story 2.1's "all color pairings meeting WCAG AA contrast."

### Deferred

- [x] [Review][Defer] Screen-reader announcement in `alert()`/`completion()` fires synchronously before the paired visual state change has committed/painted — a low-vision user can hear the event fractionally ahead of seeing it. Deferred: RN's native bridge timing makes this hard to guarantee either way, and the gap is sub-frame.
- [x] [Review][Defer] Completion feedback tier (haptic + announcement) fires only on the live completion transition, never on relaunch-resume landing directly on an already-complete session. Deferred as correct behavior, not a defect: re-firing a haptic buzz and "Session complete" announcement for a screen the user is passively viewing (no action just taken) would be a false/jarring signal, not a fix.

### Dismissed (false positives / already-resolved)

- "Unconditional overwrite of any existing session on a different segment" (Blind Hunter) — `session/[id].tsx:65-79`'s effect explicitly checks `session?.segmentId === segment.id` before calling `start()`; a genuinely different segment's session is preserved, not overwritten by this code path. The comment's reliance on `app/index.tsx` resolving other cases first is accurate: `index.tsx` is the only entry point that reaches this screen with a stale different-segment session already unresolved, and it always shows Resume/Discard first.
- "`started` ref guard keyed to mount, not to segment/id" (Blind Hunter) — Expo Router's dynamic segment routes (`session/[id].tsx`) unmount and remount on a param change under the Stack navigator used here (`src/app/_layout.tsx`); the scenario requires an instance-reuse behavior this app's navigator doesn't exhibit.
